## I. Introduction

随着主内存价格持续下降，越来越多 OLTP 系统将活跃数据集常驻内存，磁盘 I/O 不再是瓶颈。然而一个瓶颈消除后，新的瓶颈就会出现 —— **lock manager**。有研究报告称，在主内存 DBMS 中，事务执行时间的 16%-25% 花在与锁管理器交互上 [12]；多核竞争下这个比例还会更高 [14,22,29]。

传统 lock manager 的实现方式：哈希表将 key 映射到锁请求链表，链表前有锁头（lock head）维护当前锁状态和 mutex。每次加锁需要：哈希查找 → 获取 mutex → 临界区内插入链表。每次解锁还需要：遍历链表判断下一个谁该继承锁。

这些操作在主内存场景下不再可忽略 —— 额外的内存访问、cache miss、CPU 周期、临界区开销，可能接近甚至超过事务逻辑本身的成本。

论文的核心命题是：

> 能不能把悲观锁机制的管理结构做得非常轻，甚至删除其中大部分传统组件？

## II. VLL: Very Lightweight Locking

### 2.1 核心设计

VLL 与传统 lock manager 有两个根本区别：

**第一，锁信息与数据共存。** 每条记录旁边只放两个整数计数器：

- `C_X`：请求排他锁的事务数
- `C_S`：请求共享锁的事务数

当没有事务访问记录时，二者均为 0。

**第二，不维护 per-lock 请求队列。** 每个分区只维护一个全局队列 `TxnQueue`，按事务请求锁的顺序记录所有活跃事务。

### 2.2 执行流程

1. 事务进入临界区前，先以"不提供隔离"的方式做探索性读，推断读写集
2. 在临界区内：
    - 请求全部锁（对相应记录的 `C_X` 或 `C_S` 加一）
    - 插入 `TxnQueue`
3. 离开临界区后：
    - 排他锁可用条件：`C_X = 1` 且 `C_S = 0`
    - 共享锁可用条件：`C_X = 0`

事务分为两类：

| 状态 | 含义 |
|:---:|:---|
| `free` | 立即拿到了全部锁，可以立刻执行 |
| `blocked` | 至少一把锁没拿到，留在 `TxnQueue` 中等待 |

### 2.3 正确性保证：队首事务一定能执行

> 每个事务在同一个临界区内完成"请求全部锁 + 入队"。

因此，如果某个事务已经来到 `TxnQueue` 队首，说明所有比它更早入队的事务都已经完成。比它更晚入队的事务如果与它冲突，自己会被阻塞住。所以队首事务永远不会卡死。

这个性质带来两个直接结果：

- 分区内不会死锁
- VLL 不需要维护传统的 per-lock waiting queue

### 2.4 队列大小控制

随着 `TxnQueue` 变长，新事务与队列中任一事务冲突的概率增加。论文设置阈值限制队列大小，且阈值按 **blocked 事务数**而非总队列长度控制，使得高冲突负载更早触发限制。

## III. Trade-offs

VLL 的主要优势是极低的开销：把标准锁管理器的请求链表压缩成两个整数，且与数据共存于同一 cache line。

主要代价是**信息损失导致并发度下降**。VLL 没有锁请求队列，只能检查：
(a) 该锁请求是否唯一，或 (b) 该事务是否已足够老。

经典例子：

| 事务 | 写集 |
|:---:|:---:|
| A | `x` |
| B | `y` |
| C | `x, z` |
| D | `z` |

A、B 运行中，C 因与 A 在 `x` 冲突而阻塞，D 因与 C 在 `z` 冲突而阻塞。A 完成后，标准锁管理器能判断 C 已经在所有请求队列队首、可以放行；但 VLL 只看到 `z` 上 `C_X = 2`，不知道其中一个请求属于 C 自己，因此无法立即判断。

## IV. SCA: Selective Contention Analysis

SCA 是 VLL 的补偿机制，在 CPU 否则空闲时按需恢复部分依赖分析。

### 4.1 触发时机

- `TxnQueue` 已满
- 没有显然可执行的事务
- CPU 否则就要空转

### 4.2 算法

SCA 从 `TxnQueue` 队首开始扫描，维护两个 100 kB 位图（可放入 256 kB L2 cache）：

- `D_X[j] = 1`：已扫描事务的写集中有元素哈希到位置 `j`
- `D_S[k] = 1`：已扫描事务的读集中有元素哈希到位置 `k`

当前扫描到的事务 `T_next` 若满足：

- 读集所有 key 的 `D_X[hash] = 0`
- 写集所有 key 的 `D_X[hash] = 0`
- 写集所有 key 的 `D_S[hash] = 0`

则可以安全执行。

### 4.3 Selective 的两层含义

1. 不是一直开着，只有必要时才触发
2. 不做完整 all-to-all 依赖分析，优先检查最老、最可能可执行的事务

SCA 的位图哈希可能产生 **false negative**（保守地认为有冲突），但不会产生 **false positive**（错误放行），正确性不受影响。

### 4.4 实现优化

首次 SCA 遇到某事务时，将其读写集哈希结果缓存到事务状态里；后续扫描复用以避免重复哈希。

## V. VLL 的两种实现形式

| 形式 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| Colocated VLL | `C_X`/`C_S` 直接放在记录旁边 | 数据与锁一起进 cache，局部性最优 | 锁管理线程也会把数据带入 cache 造成污染 |
| Arrayed VLL | 锁计数器放在独立连续数组里 | 对专门的 lock manager thread 更友好 | 额外访存 |

## VI. VLLR: 范围锁扩展

VLLR 将 VLL 扩展到范围锁：

1. 将 key range 表示为 bitstring 范围，转换为前缀集合
2. 每个 key/前缀维护四类计数器：`C_X`、`C_S`、`I_X`（意向排他）、`I_S`（意向共享）
3. 锁前缀 `p` 时，在 `p` 上增加 `C_X`/`C_S`，在所有非空严格前缀上增加 `I_X`/`I_S`
4. 锁管理成本与锁定的前缀位数成正比，而非与范围切分区间数成正比

## VII. 关键实验结论

### 7.1 纯锁 CPU 成本

| 方案 | 每事务锁 CPU 成本 |
|:---|:---:|
| Traditional 2PL | 21.07 us |
| Deterministic Calvin | 20.18 us |
| Multi-threaded VLL | 1.83 us |
| Single-threaded VLL | 0.69 us |

差距一个数量级。

### 7.2 单机多线程

| 方案 | long 事务锁开销 | short 事务锁开销 |
|:---|:---:|:---:|
| Traditional 2PL | ~22% | ~43% |
| VLL | ~1.5% | ~10.2% |

中高冲突下，SCA 可将 VLL 吞吐最多提升约 41%。

### 7.3 分布式

- partition-per-core：高冲突下 SCA 相对普通 VLL 提升约 100%-130%（比单机更大，因为队首事务可能在等远端结果）
- partition-per-machine：对短事务，Deterministic VLL 相比原生 Calvin 最高可提升约 2.3×
- TPC-C：VLL + SCA 相对哈希锁方案仍有约 8% 吞吐提升

### 7.4 VLL 与 Calvin 的契合

Calvin 在事务执行一开始就锁住全部数据，这恰好满足 VLL 对锁请求顺序的要求。VLL 放进 Calvin 后，消除了锁线程瓶颈，对短事务效果尤其明显。

## VIII. 局限

1. **依赖事务提前知道读写集** — 探索性读预测失误会 abort/restart
2. **极高冲突下未必最优** — 传统锁队列的精确信息重新变得有价值
3. **优化的是锁管理，不是整个分布式事务协议** — 若瓶颈在 2PC/网络，VLL 收益变小
4. **SCA 虽按需触发，但仍有扫描和哈希成本**
5. **VLLR 的前缀近似是保守的** — 可能锁到比真实范围更大的区域

## IX. 总结

> VLL 的价值不在于"发明了一把更快的锁"，而在于它证明了：在主内存数据库中，锁管理器真正长期需要维护的信息，比传统设计假设的要少得多。

核心洞察：

1. 用极简计数器和事务顺序替代复杂锁队列
2. 诚实处理 trade-off — 更轻量意味着信息更少，所以用 SCA 按需补偿
3. 与 deterministic 系统（Calvin）天然契合，能产生 1 + 1 > 2 的效果
